    # Azure 기반 물류센터 컨베이어 레일 시스템 아키텍처 및 데이터 모델 설계서
    
    ## 1. 개요
    
    이 문서는 Azure 기반 물류센터 컨베이어 벨트 레일 시스템의 전체 아키텍처와 데이터 모델(테이블 구조, 지표 커버리지)을 정리한 설계 문서이다.  
    IoT 센서/장비에서 발생하는 이벤트를 Azure IoT Hub–Stream Analytics–DB–Data Lake/Synapse/Fabric–Web App으로 처리하고, 운영·분석·예측·시뮬레이션까지 확장하는 것을 목표로 한다.
    
    ---
    
    ## 2. 주요 컴포넌트별 설계
    
    ### 2.1 IoT 센서 및 IoT Hub
    
    - 센터별/라인별/구간별/센서별 Device 등록 및 관리  
    - 바스켓, 병목, 컨테이너, 차량 등 다양한 센서 이벤트 수집  
    - 메시지 라우팅: 센터별/라인별로 구분된 메시지 라우팅 정책 적용 (예: Hub 라우팅, 메시지 속성 기반 라우팅)
    
    ### 2.2 Azure Stream Analytics (ASA)
    
    - 실시간 이벤트 처리: 병목 감지, 대기 시간 계산, KPI 산출  
    - 이벤트 트리거: 임계치 초과 시 알림(Logic App, Functions, Event Grid 등), 자동 조치  
    - Output: Azure PostgreSQL / Azure SQL / Data Lake 등 다중 Output 구성
    
    ### 2.3 데이터 저장 (Azure PostgreSQL, Azure SQL)
    
    - 센터별, 라인별, 구간별, 이벤트별 테이블 설계  
    - Hot/Cold 데이터 분리, 파티셔닝, 인덱싱 전략 수립  
    - KPI, 병목, 손실, 집계 데이터 저장용 스키마 구성
    
    ### 2.4 데이터 레이크/웨어하우스 (Data Lake, Synapse, Fabric)
    
    - 대용량 원천 데이터 저장, 장기 이력 데이터 관리  
    - ETL/ELT 파이프라인: Raw → Clean → Aggregated  
    - 집계, 트렌드, 예측, AI/ML 분석 및 시뮬레이션 지원
    
    ### 2.5 Web App (대시보드)
    
    - 실시간 현황, KPI, 병목, 손실, 집계 데이터 시각화 (그래프, 히트맵, 표 등)  
    - 센터/라인/구간별 커스텀 설정, 프리셋 관리 UI  
    - 사용자/권한 관리, 알림(메일/SMS/Push), 모바일 대응
    
    ### 2.6 자동화 및 운영
    
    - IaC(Bicep/Terraform)로 인프라 및 플랫폼 리소스 자동 배포  
    - CI/CD: Azure DevOps, GitHub Actions로 애플리케이션/ASA/DB 스키마 배포 자동화  
    - 모니터링: Azure Monitor, Application Insights, Log Analytics  
    - 장애 복구: Azure Site Recovery, Geo-Replication, 백업/복구 정책

    ## 3. 데이터 모델/이벤트 구조 확장 및 고도화 설계
    
    ### 3.1 센서/이벤트 공통 구조
    
    공통 필드 예시:
    
    - 공통: `event_id`, `event_type`, `occurred_at`, `center_id`, `zone_id`, `line_id`, `section_id`, `sensor_id`  
    - 대상 객체 ID: `basket_id`, `container_id`, `vehicle_id` 등 (nullable)  
    - 작업자 정보: `worker_id` (nullable)  
    - 병목 관련: `duration_sec`, `cause`, `affected_basket`, `result`, `detail_reason` 등  
    - 센서/장비 상태: `status`, `error_code`, `error_message` 등  
    - 이벤트 간 연관: `prev_event_id`, `next_event_id`, `route_id` 등  
    - KPI/손실/트렌드 분석용: `target_value`, `sla`, `predicted_value` 등  
    
    이 공통 구조를 기반으로, 아래와 같이 마스터/이벤트/이력 테이블을 설계한다.

    ## 4. 테이블 구조 설계
    
    ### 4.1 센터/존/라인/구간/센서 마스터
    
    #### 4.1.1 개요
    
    | 테이블 | 목적 | 주요 컬럼 | 비고 |
    | --- | --- | --- | --- |
    | center | 물류센터(사이트) 정의 | center_id, name, location, status, opened_at | 상위 엔터티(Site) |
    | zone | 센터 내 존/구역 | zone_id, center_id, name, type, status | 피킹존, 적치존 등 |
    | line | 컨베이어 라인 단위 | line_id, center_id, name, type, status | 메인/서브 라인 구분 |
    | section | 라인 내 구간 | section_id, line_id, name, order_in_line, type | 병목·체류 시간 분석 단위 |
    | sensor | 센서/장비 센싱 포인트 | sensor_id, section_id, equipment_id, sensor_type, name, status | 속도/존재/환경 센서 구분 |
    
    #### 4.1.2 예시 DDL
    
    ```sql
    CREATE TABLE center (
      center_id   BIGSERIAL PRIMARY KEY,
      name        VARCHAR(100) NOT NULL,
      location    VARCHAR(200),
      status      VARCHAR(20),
      opened_at   DATE
    );
    
    CREATE TABLE zone (
      zone_id   BIGSERIAL PRIMARY KEY,
      center_id BIGINT NOT NULL REFERENCES center(center_id),
      name      VARCHAR(100),
      type      VARCHAR(50),
      status    VARCHAR(20)
    );
    
    CREATE TABLE line (
      line_id   BIGSERIAL PRIMARY KEY,
      center_id BIGINT NOT NULL REFERENCES center(center_id),
      name      VARCHAR(100),
      type      VARCHAR(50),
      status    VARCHAR(20)
    );
    
    CREATE TABLE section (
      section_id    BIGSERIAL PRIMARY KEY,
      line_id       BIGINT NOT NULL REFERENCES line(line_id),
      name          VARCHAR(100),
      order_in_line INT,
      type          VARCHAR(50)
    );
    
    CREATE TABLE sensor (
      sensor_id    BIGSERIAL PRIMARY KEY,
      section_id   BIGINT REFERENCES section(section_id),
      equipment_id BIGINT,
      sensor_type  VARCHAR(50),
      name         VARCHAR(100),
      status       VARCHAR(20)
    );

### 4.3 센서 이벤트(sensor_event)

#### 4.3.1 목적 및 특징

* IoT 센서/장비에서 발생하는 모든 이벤트·측정값 로그 저장
* 고빈도 쓰기, 시간 파티셔닝, Hot/Cold 분리, JSON 확장 필드 포함

#### 4.3.2 컬럼 정의

| 컬럼명 | 타입  | 설명  |
| --- | --- | --- |
| event_id | BIGSERIAL (PK) | 이벤트 ID |
| event_type_code | VARCHAR(50) | 이벤트 타입 코드(도착, 출발, 오류 등) |
| occurred_at | TIMESTAMP | 발생 시각 |
| center_id, zone_id, line_id, section_id | BIGINT | 위치 정보 |
| sensor_id | BIGINT | 센서 ID |
| basket_id, container_id, vehicle_id | BIGINT | 대상 객체 ID(바스켓/컨테이너/차량) |
| worker_id | BIGINT | 관련 작업자 |
| numeric_value | DOUBLE PRECISION | 측정값(수치형) |
| string_value | VARCHAR(200) | 측정값/상태(문자형) |
| status | VARCHAR(20) | 센서/장비 상태 |
| error_code, error_message | VARCHAR | 오류 정보 |
| prev_event_id, next_event_id | BIGINT | 이전/다음 이벤트 참조 |
| route_id | BIGINT | 이동 경로 ID |
| target_value, sla, predicted_value | DOUBLE PRECISION | KPI/목표/예측값 |
| attributes_json | JSONB | 확장 속성(유연한 스키마) |

#### 4.3.3 예시 DDL

    CREATE TABLE sensor_event (
      event_id        BIGSERIAL PRIMARY KEY,
      event_type_code VARCHAR(50) NOT NULL,
      occurred_at     TIMESTAMP NOT NULL,
      center_id       BIGINT NOT NULL,
      zone_id         BIGINT,
      line_id         BIGINT,
      section_id      BIGINT,
      sensor_id       BIGINT,
      basket_id       BIGINT,
      container_id    BIGINT,
      vehicle_id      BIGINT,
      worker_id       BIGINT,
      numeric_value   DOUBLE PRECISION,
      string_value    VARCHAR(200),
      status          VARCHAR(20),
      error_code      VARCHAR(50),
      error_message   VARCHAR(500),
      prev_event_id   BIGINT,
      next_event_id   BIGINT,
      route_id        BIGINT,
      target_value    DOUBLE PRECISION,
      sla             DOUBLE PRECISION,
      predicted_value DOUBLE PRECISION,
      attributes_json JSONB
    );

### 4.4 병목 이벤트(bottleneck_event)

#### 4.4.1 목적 및 특징

* 병목 구간·지연 이벤트를 요약해 관리하고, 원인/영향 분석에 활용
* 요약 이벤트 + 관련 sensor_event 맵핑 구조

#### 4.4.2 컬럼 정의

| 컬럼명 | 타입  | 설명  |
| --- | --- | --- |
| bottleneck_id | BIGSERIAL (PK) | 병목 이벤트 ID |
| root_event_id | BIGINT | 대표/트리거 이벤트 ID |
| occurred_at | TIMESTAMP | 병목 발생 시각(시작) |
| center_id, zone_id, line_id, section_id | BIGINT | 위치 정보 |
| sensor_id | BIGINT | 대표 센서 |
| duration_sec | BIGINT | 지속 시간(초) |
| cause_code | VARCHAR(50) | 병목 원인 코드(장비, 작업자, 설계 등) |
| affected_basket | BIGINT | 영향 받은 바스켓 |
| result_code | VARCHAR(50) | 처리 결과 코드 |
| detail_reason | VARCHAR(500) | 상세 사유 |
| worker_id | BIGINT | 담당 작업자 |
| status | VARCHAR(20) | 처리 상태 |
| error_code, error_message | VARCHAR | 관련 오류 |

#### 4.4.3 예시 DDL

    CREATE TABLE bottleneck_event (
      bottleneck_id   BIGSERIAL PRIMARY KEY,
      root_event_id   BIGINT,
      occurred_at     TIMESTAMP NOT NULL,
      center_id       BIGINT NOT NULL,
      zone_id         BIGINT,
      line_id         BIGINT,
      section_id      BIGINT,
      sensor_id       BIGINT,
      duration_sec    BIGINT,
      cause_code      VARCHAR(50),
      affected_basket BIGINT,
      result_code     VARCHAR(50),
      detail_reason   VARCHAR(500),
      worker_id       BIGINT,
      status          VARCHAR(20),
      error_code      VARCHAR(50),
      error_message   VARCHAR(500)
    );
    
    CREATE TABLE bottleneck_event_sensor (
      bottleneck_id BIGINT NOT NULL REFERENCES bottleneck_event(bottleneck_id),
      event_id      BIGINT NOT NULL,
      PRIMARY KEY (bottleneck_id, event_id)
    );

## 5. 도출 가능한 주요 지표 및 분석 항목

### 5.1 처리량/흐름 관련

* 센터/존/라인/구간/센서별 단위 시간(분/시간/일)별 처리량
* 시간대별, 요일별, 월별 처리량 트렌드
* 센터/라인/구간별 TOP N 처리량 구간
* 실시간/집계 처리량 변화 추이

### 5.2 병목/지연/이상 관련

* 병목 이벤트 발생 빈도, 지속 시간, 주요 발생 구간/라인/시간대
* 병목 원인별(센서, 장비, 작업자 등) 통계
* 병목/지연으로 인한 생산성 손실 추정
* 비정상 이벤트(센서 오류, 장비 고장 등) 발생률
* 실시간 이상 감지/알림 이벤트

### 5.3 KPI/성과/효율 관련

* 평균 처리 시간, 평균 대기 시간, 평균 이동 거리
* SLA(서비스 수준) 준수율, 목표 대비 실적
* 작업자별/장비별 성과 및 효율성
* 센터/라인/구간별 KPI 달성률

### 5.4 객체/경로/이력 분석

* 바스켓/컨테이너/차량별 이동 경로 및 처리 이력
* 객체별 체류 시간, 이동 거리, 처리 단계별 소요 시간
* 작업자별 작업 이력, 장비별 가동/비가동 이력

### 5.5 트렌드/예측/AI 분석

* 시간대/요일/월별 트렌드 분석
* AI/ML 기반 병목/이상 예측, 수요 예측
* KPI/이상/병목 등 미래 예측 및 시뮬레이션

### 5.6 운영/설비/유지보수·ESG·비용

* 장비별 가동률, 고장률, 평균 무고장 시간(MTBF), 평균 수리 시간(MTTR)
* 센서/장비별 점검 이력, 예방 정비 필요 예측
* 센터/라인/구간별 운영비용, 인건비, 에너지비, 유지보수비
* 에너지 사용량, 탄소 배출량 추정, 환경 센서 기반 ESG 지표

### 5.7 고객/서비스/품질 및 외부 연계

* 주문별 처리 리드타임, 배송 지연률, SLA 위반 건수
* 고객별/상품별 처리 현황, 클레임/반품률 (추가 테이블 연계)
* 날씨/교통/공휴일 등 외부 요인과의 상관 분석

## 6. 지표별 데이터 구조 커버리지 점검

| 지표/분석 항목 | 현재 데이터 구조로 가능 여부 | 비고/확장 필요시 설명 |
| --- | --- | --- |
| 센터/구역/라인/구간/센서별 처리량, 트렌드, TOP N | 가능 | event_type, occurred_at, center_id 등 활용 |
| 병목 이벤트, 원인별 통계, 생산성 손실, 이상 이벤트 | 가능 | bottleneck_event, cause, duration_sec 등 활용 |
| KPI/성과/효율, SLA, 목표 대비 실적 | 가능 | target_value, sla, worker_id 등 활용 |
| 바스켓/컨테이너/차량/작업자/장비별 경로·이력 | 가능 | basket_id, container_id, vehicle_id, prev_event_id, next_event_id 등 활용 |
| 트렌드/예측/AI 분석 | 가능 | occurred_at, predicted_value 등 활용, AI/ML은 추가 피처 필요 시 확장 |
| TOP N 병목, 실시간 알림, 신규 이벤트/상태별 통계 | 가능 | event_type, status 등 활용 |
| 장비 가동률, 고장률, MTBF/MTTR | 부분 가능 | status, error_code 등 활용, 정비/부품/재고 이력은 별도 테이블 필요 |
| 환경 센서 데이터 | 가능 | sensor_event에 센서 타입 추가 필요 |
| 에너지/탄소/ESG | 확장 필요 | 별도 테이블 및 외부 연동 필요 |
| 안전사고/품질/리스크 | 부분 가능 | 이상 이벤트/불량은 가능, 품질·리스크 세부 이력은 별도 테이블 필요 |
| 운영비용/ROI/경영 요약 | 확장 필요 | 비용/ROI 등은 별도 테이블 및 연동 필요 |
| 주문/클레임/반품/서비스 품질 | 확장 필요 | 주문/클레임/반품 등은 별도 테이블·시스템 연동 필요 |
| IoT 메시지 성공률, 장애/복구, 데이터 품질 | 부분 가능 | 이벤트 수집/오류 이벤트로 일부 가능, 시스템 장애/복구/품질 모니터링은 별도 테이블 필요 |
| 시뮬레이션/디지털 트윈 | 부분 가능 | event 데이터 활용 가능, 시뮬레이션/트윈 결과는 별도 테이블 필요 |
| 외부 데이터(날씨, 교통, 공휴일 등) 연계 | 확장 필요 | 별도 테이블/연동/ETL 필요, 센터/이벤트 데이터의 날짜·지역 등과 조인 |

## 7. 구현 단계별 상세 플랜

### 7.1 1단계: 요구사항 분석 및 설계

* 센터별/라인별/구간별 구조 및 데이터 흐름 정의
* KPI, 병목, 손실 등 주요 지표 정의
* 데이터 모델 및 API 설계, 보안 요구사항 반영

### 7.2 2단계: Azure 리소스 구축

* IoT Hub, ASA, PostgreSQL, SQL, Data Lake, App Service 등 배포
* 네트워크, 보안, 인증(Entra ID, Key Vault, Private Endpoint, NSG 등) 설정

### 7.3 3단계: 데이터 수집 및 처리 구현

* IoT 센서 시뮬레이터/실장, IoT Hub 연동
* ASA 쿼리 작성, 실시간 이벤트 처리/알림 로직 구현
* 데이터베이스 테이블/뷰/프로시저 구축

### 7.4 4단계: 데이터 분석 및 집계

* ETL/ELT 파이프라인 구현(Data Factory, Synapse 등)
* KPI, 병목, 손실, 집계 데이터 자동화
* AI/ML 분석(예측, 이상 탐지 등) PoC 및 점진적 고도화

### 7.5 5단계: 웹 대시보드 및 시각화

* 실시간/집계 데이터 시각화(그래프, 표, 히트맵 등)
* 커스텀 설정, 프리셋, 알림, 권한 관리 UI
* 모바일/다국어 대응, 사용자 경험 고도화

### 7.6 6단계: 운영 및 고도화

* 모니터링, 장애 대응, 백업/복구 체계 구축
* 데이터 품질 관리, 보안·컴플라이언스 강화
* AI/머신러닝, 디지털 트윈, 글로벌 확장 등 고도화

## 8. 권장 Best Practice

* 확장성·유연성: 마이크로서비스/이벤트 기반, 스키마 확장 가능한 설계
* 보안: 전 구간 암호화, RBAC/최소 권한, Key Vault, 네트워크 격리
* 데이터 품질: 스키마 검증, 이상치/결측 모니터링, 데이터 카탈로그
* 자동화: IaC, CI/CD, 테스트 자동화
* 표준화/거버넌스: 코드/마스터 관리, 명명 규칙, 데이터 소유자 정의
* 외부 연동/ESG/AI: 날씨/교통/공휴일/에너지 데이터 연계, ESG 지표, 예측/최적화 모델 반영
